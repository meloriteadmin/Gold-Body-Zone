# Gold Body Zone / IRONSTAGE

React/Vite frontend, Express API, PostgreSQL/Prisma, local image storage, SMTP, and Cashfree payments.

## Local development

Install dependencies with `npm ci` in `backend` and `frontend`. Copy `backend/.env.example` to `backend/.env` and supply a local PostgreSQL URL and unique secrets. Run `npm run prisma:generate` and `npm run prisma:deploy` in `backend`, then start backend and frontend with `npm run dev`. Vite proxies `/api` to the backend. The backend seeds default competitions only in development when the database is empty. Public registrations stay closed until an administrator publishes and opens a competition.

## VPS preparation

Use a Linux VPS with Docker Compose, host Nginx, a domain, and a valid TLS certificate. Copy `.env.production.example` to `.env.production` on the VPS, replace every placeholder, and keep it readable only by the deploying account. Use separate random values for `POSTGRES_PASSWORD`, `CHECKOUT_TOKEN_SECRET`, and `AADHAAR_ENCRYPTION_KEY` on a fresh installation. **For an existing database**, the previous Aadhaar encryption seed was the old `AADHAAR_ENCRYPTION_KEY` value or, when unset, the old storage provider's service key. Set the new `AADHAAR_ENCRYPTION_KEY` to that exact seed until records can be deliberately re-encrypted; otherwise old encrypted values are unreadable and duplicate detection changes. The previous checkout token seed was the Cashfree secret when present. To preserve outstanding 24-hour status links during cutover, temporarily use that exact value as `CHECKOUT_TOKEN_SECRET`, then rotate after links expire and pending payments are reconciled. Protect these values as secrets. Keep the PostgreSQL URL password consistent with `POSTGRES_PASSWORD`; percent-encode URL special characters. Configure SMTP before starting the backend. Do not put secrets in the React build.

Before migrating an **existing** database, take a verified backup and record the current Prisma migration history. Historical migration files were adapted for plain PostgreSQL; an existing database may report checksum drift. Review `prisma migrate status` and the backup before applying migrations. Never use `prisma migrate reset`, `db push`, or automatic seeding against production. Existing admin passwords from the previous provider cannot be recovered. Provision a local password for each existing admin by email after migration using `backend/src/scripts/provisionAdmin.js --email admin@example.com --password-file /path/to/password-file`. The password file must have mode 0600 and be accessible inside the backend container only temporarily. The script updates the matching profile without replacing its role or records. Test login and password reset before DNS cutover.

Existing external image URLs remain in the database so records are not destroyed. **Import and verify all historical posters, event photos, and avatars before disconnecting the old image host.** After backing up both the database and images, run `node src/scripts/importRemoteImages.js --origin=https://OLD_IMAGE_HOST` in the backend container for a dry run; repeat with `--apply` to copy matching public images and update their references. The script rejects redirects and files above 5 MiB, and reports any failures. Verify that it finds zero remaining references on a final dry run. Keep the old image host available until every reference is checked. Private or unavailable legacy files require a separate manual export.

For older local `/uploads/...` URLs, run `node src/scripts/importLegacyLocalImages.js --origin=http://OLD_HOST:PORT --source-root=/absolute/old/uploads` first as a dry run and then with `--apply` on a backed-up, isolated database copy. The importer copies files and updates references; it does not delete the source files. Run `node src/scripts/reconcileImages.js` to list unreferenced uploads older than 24 hours; `--apply` removes only those files after a fresh database reference check. Review its output and backup before applying it.

An existing database can contain three known historical migration checksum differences. Run `node src/scripts/checkMigrationHistory.js` against the restored copy; it fails on unknown drift. The forward-only `0011_reconcile_legacy_local_auth` migration creates missing admin sessions without dropping legacy admin identifiers. The old `participant_accounts` table is retained as archived data. Apply only reviewed migrations after a restore test; never edit `_prisma_migrations` to hide drift.

## Deployment

1. Create `data/uploads` with ownership writable by container UID 1000 and restrictive permissions. Keep it on persistent storage. `postgres_data` is a persistent Docker volume. Allocate separate disk space for OS, PostgreSQL WAL/maintenance/temp files, and backups.
2. Validate with `docker compose --env-file .env.production config`. Build with `docker compose build`. Start the database with `docker compose up -d db`, run `docker compose run --rm backend npx prisma migrate deploy`, then start the app with `docker compose up -d backend frontend`. Check `docker compose ps`, backend `/health`, logs, admin login, and the storage dashboard.
3. Install `deploy/nginx-host.conf.example` as the host Nginx site after replacing the domain and certificate paths. Obtain a valid certificate, test Nginx configuration, and reload it. Open only 80/443 and restricted SSH in the VPS firewall. The database has no published port; app ports bind to loopback only. Set the Cashfree webhook URL to `https://YOUR_DOMAIN/api/webhooks/cashfree` and verify sandbox events before opening registrations.
4. Check the HTTPS origin exactly matches `PUBLIC_APP_URL` and `CORS_ORIGIN`. One trusted host Nginx proxy sets forwarded headers; `TRUST_PROXY=1` in Compose. Admin cookies are HttpOnly and Secure in production. Rotate secrets and admin passwords after any exposure.
5. For a separate HTTPS staging domain, set `STAGING_MODE=true` and `CASHFREE_ENV=sandbox` with sandbox credentials. Keep the production domain and credentials separate. Before opening registrations, verify desktop and mobile registration, Cashfree sandbox success/failure/cancellation/retry/refund/webhook replay, admin record consistency, SMTP receipt, image persistence across a container rebuild, backup restoration, and disk alerts. Do not switch live payment configuration or initiate live transactions without authorization.

## Storage and backups

The API enforces an application-wide image upload quota of **1 GiB**, including files already in `data/uploads`. It validates actual JPEG, PNG, or WebP content (maximum 5 MiB each), serializes quota decisions, and deletes files when their records are removed. The dashboard reports usage and last measurement. Monitor disk usage outside the app as well.

PostgreSQL has **no native hard per-database 500 MiB limit**. The dashboard measures `pg_database_size` against 500 MiB and warns at 70%, 85%, and 95%. At 95%, selected nonessential new competition/image metadata is paused. Critical payment, recovery, and security writes continue. Expired admin sessions and reset tokens are cleaned daily; registration, payment, refund, invoice, and audit records are never automatically purged. Keep ample free disk for WAL, VACUUM, temporary files, and system services; configure VPS disk alerts independently.

Store database dumps and image archives **outside** the active database and `data/uploads`, preferably encrypted off-server. Example backup: `docker compose exec -T db pg_dump -U gbz -Fc gold_body_zone > /secure-backups/gbz-$(date +%F).dump`; archive `data/uploads` to a separate location. Restore **into a new isolated database and upload directory first**, then verify counts, key records, image references, login, and payment history. Never test restoration by replacing the live database. Automate backups, retention, and restoration drills for the VPS.

## Verification commands

Run `npm test`, `npm run prisma:generate`, and `npx prisma validate` in `backend`; run `npm run build` in `frontend`; run `npm audit --omit=dev` in both. Automated tests and a local migration smoke test cannot establish live VPS, TLS, SMTP, historical image migration, or Cashfree sandbox readiness by themselves.
