## Fixes completed

1. **Migration reconciliation:** Restored the existing local `gold_body_zone` database into `gbz_existing_copy_20261120` without touching the original. Five pending migrations applied there. The copy exposed that an older recorded local-auth migration had never created `admin_sessions`; forward-only migration `0011_reconcile_legacy_local_auth` creates it and makes the legacy auth ID nullable without erasing values. Migration `0010_add_refund_ledger` adds refund history. Migration `0012_align_schema_defaults` resolves fresh-schema foreign-key/default drift. `checkMigrationHistory.js` permits only the three exact, inspected legacy checksum pairs and fails unknown drift. Prisma history was **not** rewritten or reset.
2. **Cashfree order reservation:** A row lock on the registration serializes first-order creation. The order ID is stable (`CF-<registration UUID>`) and the request uses a stable UUID idempotency key. Timeout recovery checks that same remote order and amount; it never generates a replacement order. Existing paid/active/expired-order behavior is preserved. The earlier payment-row lock still prevents delayed failure from downgrading paid status.
3. **Refunds:** Added `Refund` records with requested, pending, success and failed states, unique merchant/provider IDs, amount, note, admin actor and timestamps. Only `SUPER_ADMIN` can initiate/reconcile; ordinary admins can read history. Repeated requests require the same UUID and details. Reservation prevents over-refunding across concurrent requests. Provider response, signed webhook and reconciliation update the ledger idempotently. Partial success retains `PAID`; only cumulative full success marks payment `REFUNDED` and registration `CANCELLED`. A general payment-status update cannot mark a payment refunded without matching successful ledger entries. Failed refunds remain recorded and release capacity for a new request. The original payment record/history is retained.
4. **Images/build:** The upload lock now has a heartbeat, stale-lock recovery and inode ownership check. `reconcileImages.js` is dry-run by default and checks database references before optional deletion of orphan images older than 24 hours. Added a dry-run-first importer for old local `/uploads/...` URLs. Regenerated the frontend lockfile in a clean Linux container; both Linux Docker and macOS `npm ci` builds now succeed.
5. **Admin and staging controls:** Fixed the registration detail modal's status-update callback. Added `STAGING_MODE` and a default-closed staging registration gate. Cashfree sandbox is allowed with production security settings only on an explicitly configured staging installation.

## Remaining staging verification gates

These are **post-staging-deployment checks**, not claims of completed verification:

1. Confirm actual Hostinger KVM 4 OS, Docker/Compose, disk and RAM; use a separate staging domain with valid HTTPS and restricted access. Hostinger's published KVM 4 limits are 4 vCPU, 16 GB RAM and 200 GB NVMe, subject to the actual hPanel allocation. [Hostinger limits](https://support.hostinger.com/en/articles/6976044-parameters-and-limits-of-hosting-plans).
2. Restore a current database backup to staging and run `checkMigrationHistory.js`, `prisma migrate status`, `prisma migrate deploy`, and a schema diff there. Any **unknown** checksum drift or schema difference needs investigation before migration. Retain archived legacy tables/columns and all participant/payment records. Test an isolated restore before changing any production source.
3. Import images from backed-up source storage. Run both importers in dry-run mode first; verify each expected image and zero remaining legacy references. Keep source files until after verification. Test container rebuild/restart persistence, quota concurrency, orphan dry run and disk alerts.
4. Supply Cashfree **sandbox** credentials only, keep `STAGING_MODE=true`, `CASHFREE_ENV=sandbox`, and `STAGING_REGISTRATIONS_ENABLED=false` initially. After access controls and data isolation are checked, explicitly open staging registrations for test records and run real sandbox checkout, success, failure, user cancellation, retry, duplicate/delayed webhooks, admin reconciliation, full/partial/failed refunds, and order timeout/idempotency. Use Cashfree's [checkout](https://www.cashfree.com/devstudio/preview/pg/web/checkout) and [webhook verification](https://www.cashfree.com/devstudio/preview/pg/tools/webhookVerification) guidance. Close staging registrations after testing.
5. Verify desktop/mobile registration and admin dashboard in a browser, SMTP reset/confirmation delivery, HttpOnly/Secure cookies, refund permissions, Nginx forwarded headers, firewall, database isolation, host free-space alerts, encrypted off-server backups and restore. The 500 MiB database value is monitoring/guardrails, not a PostgreSQL hard limit; reserve space for WAL, maintenance and backups.

An ambiguous refund API timeout deliberately leaves its amount reserved as `REQUESTED`; repeat the same UUID request and reconcile with Cashfree before issuing another refund. Do not manually release that reservation based only on a transient lookup failure. The current 500 kB frontend bundle advisory is a performance improvement, not a staging deployment blocker.

**Production launch remains NOT READY** until those staging tests pass with actual Cashfree sandbox and the intended VPS. This work did not deploy, change the VPS, enable registrations, use live credentials, initiate a payment or delete an existing participant/payment record.
